# ベンダーロックインしない自作Wiki基盤の設計

> **問い**: この LLM Wiki を、特定ベンダー(Claude / Anthropic)に縛られない自作基盤にできるか?できるならどう作るか?
> **真の目的**(2026-07-15 に明確化): 単なるベンダー回避ではない。**LLM業界のダイナミックな変化に左右されず、その上でプロダクト価値を長期的に探索し続けられる土台**を作ること。
> **位置づけ更新**(同日): さらに前提が拡張され、Wiki は題材の一つにすぎないと判明。全体像は [[AIネイティブ価値探索基盤]] を参照。本ページはその L0(資産層)+ L1(継ぎ目層)の詳細設計にあたる。
> **出典**: 2026-07-15 の設計セッション。実装せず設計のみ。

## 目的から導かれる設計原則

**「所有すべきもの」と「借りるべきもの」を分離する。**

- **借りるもの(揮発性・コモディティ) = LLMの知能。** モデルは半年で入れ替わり、値付けも勢力図も動く。ここに設計を結合させた瞬間、業界変化がそのまま基盤の陳腐化になる。**だから薄い交換可能な継ぎ目(seam)の裏に隔離し、config の1行に落とす。**
- **所有するもの(耐久性・堀) = ①データ(`raw/`+`wiki/`)②スキーマ・ルール ③ワークフロー(ingest/query/lint の意味) ④(プロダクト化するなら)アクセス面。** 価値はここに複利で溜まる。モデルが誰であっても目減りしない。

### 核心の洞察: モデルの進化を「移行コスト」ではなく「追い風」に変える

このWikiは**`raw/` が不変**(スキーマ大原則1)で、`wiki/` はそこから**再生成可能**な派生物。この構造自体が業界変化への最強のヘッジになる。

> より賢いモデルが出る → 同じ `raw/` を再 ingest → `wiki/` が無料で質向上。

新モデルは「乗り換えねばならない負債」ではなく「既存資産を勝手に磨いてくれる資産」になる。**基盤を、モデル進化に抵抗する構造ではなく、モデル進化を吸収して得をする構造に設計する。** これが「業界変化に左右されない」の実体。

### プロダクト価値探索の土台として

プロダクトの堀はモデルではなく**蓄積データ + ワークフロー**に置く。モデルは誰でも同じものを借りられる(=差別化にならない)が、あなたの `raw/`・分類・矛盾解決の履歴は固有。プロダクト面(検索・API・UI)は**モデルではなくデータの上に**建てる。そうすればモデルを差し替えても製品は動き続ける。

## 結論(先に)

**知識資産は最初からロックインしていない。** 縛られているのは「操作するエージェント」の1点のみ。目的(業界変化への耐性 + プロダクト探索)から、下の3案は「独立度の階段」であると同時に**投資の優先順位**を持つ:

- **軽量案(AGENTS.md 標準化)** — 数分。どの AI コーディングエージェントでも運用可能に。**下地として即やる。**
- **自作CLI案(LLM差し替え式)** — 数日。**★この目的の本命。** ただし作るべきは「フルCLI」ではなく、まず**LLMを隔離する継ぎ目(adapter)**。業界変化が当たるのはこの1点だけになる。
- **完全ローカル自立案** — 上の継ぎ目があれば、config を Ollama に向けるだけ。独立プロジェクトではなく**下流のトグル**になる。

3案は排他ではなく**積層**する。軽量案が下地、CLI案がその上、ローカル案がさらに上。下から順に足せる。

## ロックイン診断(現状)

| レイヤー | 中身 | ロックイン | 移植性 |
|---|---|---|---|
| コンテンツ | `raw/`, `wiki/` = Markdown + `[[wikilink]]` + YAML frontmatter, git, `.obsidian/` | 🟢 ゼロ | git clone で完全に持ち出せる。どのツールでも読める |
| 知識のルール | `CLAUDE.md` の本文(スキーマ・操作手順) | 🟡 低 | 中身はただの散文。ファイル名 `CLAUDE.md` のみが Claude 固有 |
| コマンド | `.claude/commands/ingest.md`, `lint.md` | 🟡 低 | Claude Code のスラッシュコマンド形式。中身は「CLAUDE.md に従え」と言うだけの薄いラッパー |
| 実行エンジン | Claude Code CLI 本体(LLM) | 🔴 **真のロックイン** | ここだけが Anthropic 依存 |

**キーとなる事実**: このWikiの価値 = 蓄積された `.md`。それは純粋なオープン形式で git 管理されている。ベンダーが消えても、値上げしても、知識は1バイトも失われない。**残る課題は「誰が/何が ingest・query・lint を実行するか」だけ。**

## 案A: 軽量 — AGENTS.md 標準化(推奨の下地)

**狙い**: エージェント固有の設定を、業界標準の中立フォーマットに寄せる。特定CLIへの依存を「規約準拠」に置き換える。

### 変更点

```
CLAUDE.md            → AGENTS.md にリネーム(中身はそのまま)
CLAUDE.md            → 「@AGENTS.md を参照」だけの薄い転送ファイルとして残す
.claude/commands/*   → playbooks/ingest.md, playbooks/lint.md(素のMarkdown手順書)に本体を移し、
                       .claude/commands/* はそれを読むだけの薄いラッパーに
```

- `AGENTS.md` は複数のコーディングエージェントが読みにいく事実上の共通規約。`CLAUDE.md` はそれへの転送にする。
- 操作手順(ingest/query/lint)を `playbooks/` に素の Markdown で置く。エージェントは「playbook を読んで従え」と指示されれば、CLI 種別を問わず同じ挙動になる。

### 効果とトレードオフ

- 🟢 Claude Code / Codex / Cursor / Gemini CLI / Aider / opencode など、どのエージェントでも同じ Wiki を運用可能に。
- 🟢 コード不要・可逆・破壊なし。既存ワークフローは一切壊れない。
- 🟡 「LLMがルールを解釈して動く」構造は不変 → 実行にはいずれかのエージェント/APIが必要(=課金は各エージェント側に残る)。
- 🟡 各エージェントで挙動が微妙に揺れる(プロンプト解釈差)。playbook を具体的に書くほど収束する。

**これは「エンジンを乗り換え可能にする」案。エンジン自体は持たない。**

## 案B: 自作CLI — LLM差し替え式

**狙い**: オーケストレーション(ingest/query/lint のロジック)を自分のコードで所有し、LLM を交換可能なバックエンドに落とす。

### アーキテクチャ

```
wiki-cli/
├── wiki                    # エントリポイント(Python or TS)
├── config.yaml             # provider: claude|openai|gemini|ollama, model, api_key_env
├── core/
│   ├── ingest.py           # raw/ 走査 → 要約生成 → sources/ 生成 → entity/concept 更新 → index/log
│   ├── query.py            # index.md 読み込み → 関連ページ検索 → 回答 → answers/ 保存
│   ├── lint.py             # 矛盾・孤立ページ・リンク切れ・ギャップ検出
│   └── llm.py              # ★プロバイダ抽象化レイヤ(litellm 等)
└── prompts/                # ingest/query/lint のシステムプロンプト(= playbook の実体)
```

- **`llm.py` が要**。litellm または OpenAI互換エンドポイントで統一 → `config.yaml` の1行変更で Claude ↔ GPT ↔ Gemini ↔ ローカル を差し替え。
- ファイル操作(git・Markdown 生成・`[[wikilink]]` 整合・frontmatter 更新)は**自作コードで決定論的に**行う。LLMには「要約・分類・矛盾検出」など判断部分だけ任せる。
- `wiki ingest raw/foo.md` / `wiki query "..."` / `wiki lint` のように CLI 化。cron やエディタからも叩ける。

### 効果とトレードオフ

- 🟢 **エンジンを完全所有**。ベンダーは「差し替え可能な部品」に降格。値上げ・仕様変更・提供終了に即応できる。
- 🟢 決定論的な処理(リンク整合・index更新)がコード化され、LLMの気まぐれから解放される → 再現性・テスト可能性↑。
- 🟡 実装・保守コストが発生(初期数日 + 継続メンテ)。
- 🔴 API課金は残る(ローカルモデルにしない限り)。「ベンダー非依存」だが「LLM非依存」ではない。
- ⚠️ 矛盾: 案Aの「エージェントに解釈させる柔軟さ」を一部失う。プロンプトとコードで固めるぶん、想定外の入力に弱くなりうる。柔軟性 vs 再現性のトレードオフ。

---

## 案C: 完全ローカル自立

**狙い**: ネット・API課金・特定ベンダーを完全に断つ。

### 構成

- 案Bの CLI + `config.yaml` の provider を **`ollama`(llama.cpp)** に。
- モデルは Llama / Qwen / Gemma 等のローカル実行。埋め込みもローカル(query の関連ページ検索を意味検索にするなら)。
- git はローカル or self-host(Gitea等)。すべて手元で完結。

### 効果とトレードオフ

- 🟢 プライバシー最大(個人の仕事・プライベート知識が外部に出ない)。課金ゼロ。オフライン可。真の意味でのロックインフリー。
- 🔴 **性能がモデル依存**。要約・矛盾検出の品質はフロンティアAPIに劣る場合がある(特に長文統合・多言語)。
- 🔴 ローカル実行のハードウェア要件(VRAM等)。
- 🟡 運用はハイブリッド現実解が有力: **重い判断(topic統合)はAPI、軽い処理(分類・タグ付け)はローカル**をタスクごとに振り分け。案Bの抽象化レイヤがあれば設定で切替可能。

## 3案の比較

| 観点 | A: AGENTS.md | B: 自作CLI | C: 完全ローカル |
|---|---|---|---|
| 初期コスト | 数分 | 数日 | 数日+HW |
| ベンダー非依存 | ◎(エージェント自由) | ◎(LLM差替) | ◎◎ |
| LLM課金からの解放 | ✕ | △(選べる) | ◎ |
| 出力品質 | エージェント依存 | 選んだモデル依存 | ローカルモデル依存(やや不利) |
| 再現性・テスト性 | 低 | 高 | 高 |
| 保守負担 | ほぼゼロ | 中 | 中〜大 |
| プライバシー | 各社APIへ送信 | 選んだ先へ送信 | 外部送信なし |

## 推奨ロードマップ(目的 = 業界変化への耐性 + プロダクト探索)

原則は「所有すべき層を厚く、揮発する層を薄い継ぎ目に隔離」。この目的では**案Bの継ぎ目(adapter)が本命の投資**だが、フルCLIを先に作るのは過剰。継ぎ目から段階的に。

1. **下地 = 案A(即・無リスク)。** `AGENTS.md` 化 + `playbooks/` 化。ルールとワークフローを「所有する層」として中立フォーマットに固定。エージェント・ロックインが消え、資産の持ち出し自由も明文化される。
2. **本命 = LLM継ぎ目だけ先に作る(案Bの核)。** フルCLIではなく、まず「タスク(要約・分類・矛盾検出・統合)→ 任意モデル」を仲介する薄い adapter(litellm等)だけ。業界変化が当たる面をこの1点に集約する。プロダクト面(検索・API・UI)は後からこの下のデータ層に生やす。
3. **追い風ループを回す。** `raw/` は不変なので、より良いモデルが出るたび同じソースを再 ingest → `wiki/` が無料で改善。モデル更新を移行作業ではなく品質向上イベントに変える運用を回す。
4. **必要時のみ案C。** プライバシー・課金が主課題化したら、②の継ぎ目の config を Ollama に向けるだけ。独立プロジェクト化しない。

**やることは「所有層(データ・ルール・ワークフロー)を厚くし、モデルは薄い継ぎ目の裏に置く」。** この形が保てている限り、業界がどう動いても基盤の価値は目減りせず、プロダクト探索はデータの上で続けられる。
