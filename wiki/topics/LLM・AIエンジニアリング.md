# LLM・AIエンジニアリング

ライフエリア「技術」の統合ページ。LLM/AIエンジニアリングに関する知見をここに集約していく(進化する総説)。

原理側(論文ベースの基礎)は [[LLMの原理]] が担当。本ページは応用・実務側の受け皿。

## AIエージェントの記憶設計

現時点の理解([[LLM Wiki v2 (rohitg00)]]が初出、ソース1件):

- エージェントの長期記憶は「フラットな保存」では腐る。**ライフサイクル**(確信度・上書き・忘却)の設計が本質
- 人間の記憶モデルの転用が有力: Ebbinghaus忘却曲線、記憶4階層(作業→エピソード→意味→手続き)
- 検索は単一方式で足りない: BM25(字句)+ベクトル(意味)+グラフ(構造)のハイブリッドが定石とされる
- 関連パターン: [[LLM Wikiパターン]]、実装例: [[agentmemory]]

⚠️ 上記はソース1件のみに基づく。反証・裏付けソースの追加待ち。

## エージェントスキル設計 — 確率的システムから決定論を絞り出す

現時点の理解([[Skills For Real Engineers (mattpocock skills)]] が初出、ソース1件):

- スキルの根の徳は predictability(毎回同じプロセスを踏むこと)。設計コストは context load(常時トークン)と cognitive load(ユーザーの記憶負担)の2軸で測る — 詳細は [[スキルの書き方論(Writing Great Skills)]]
- エージェントの4大失敗モード(意図ズレ・冗長・動かない・泥団子化)には古典的処方箋が対応する。意図ズレには [[Grilling(質問駆動アライメント)]]、泥団子化には [[深いモジュール設計(Deep Modules)]]
- 1セッションを超える計画は issue tracker 上の decision ticket に分解する — [[Wayfinder(決定駆動プランニング)]]
- エージェントの記憶喪失への2解法: 知識のページ蓄積([[LLM Wikiパターン]])と語彙・決定への圧縮(CONTEXT.md + ADR = 設計判断の記録)。競合せず併用できる

## 未整理の問い

- 確信度スコアは実運用でどう校正するのか(0.85のような数値の根拠)
- 忘却(格下げ)と監査可能性(全履歴保存)はどう両立させるのか
