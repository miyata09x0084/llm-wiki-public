# なぜ wiki/ は5分類か(設計根拠)

> **問い**: wikiの分類ディレクトリ(sources/entities/concepts/topics/answers)はなぜこの設計か?
> **出典**: 2026-07-14 の設計セッションでの質疑。ソース文書ではなく設計判断の記録。

## 結論

**「知識の形式」で分けた5分類**。根拠は、カテゴリごとに「更新のされ方」と「引かれ方」が本質的に異なるため。[[LLM Wikiパターン]]の原文に暗黙に登場する成果物(entity pages, concept pages, summary, synthesis, answers)を型として明文化したもの。

## 根拠1: 更新パターンがカテゴリごとに違う

| 分類 | 更新パターン |
|---|---|
| sources/ | 一度書いたらほぼ不変(ソースのスナップショット) |
| entities/ | 事実が追記されていく(属性・関係が増える) |
| concepts/ | 定義が洗練されていく(理解の深化で書き直し) |
| topics/ | 常に書き換えられる総説(新ソースのたびに再統合) |
| answers/ | 一度書いたら不変(その時点の分析の記録) |

分類 = LLMへの更新権限の指定。混ぜると「書き換えてよいのか追記すべきか」の迷いが生じる。

## 根拠2: 形式と主題の2軸を直交させた

- **フォルダ = 形式**(entity? concept? synthesis?)— 排他的に決まる
- **タグ = 主題**(事業? 技術? 健康?)— 重複しうる。CLAUDE.md の重点領域ライフエリアと対応

主題フォルダを避けたのは、概念が複数領域に属しうる(例: LLMエージェント → 事業∧技術)ため。曖昧さの少ない軸をフォルダに、重複しうる軸をタグに割り当てた。

## 根拠3: 分類が5分岐の決定木で機械的に決まる

```
raw/ 1ファイルの要約?     → sources/
固有名詞(人・企業・ツール)? → entities/
一般概念・手法?           → concepts/
質問への回答の保存?        → answers/
それ以外(テーマの総説)     → topics/
```

分類の迷いはLint時の再分類コストに直結するため、分岐の少なさ自体が設計目標。

## 不採用案

| 代替案 | 不採用理由 |
|---|---|
| フラット(フォルダなし) | LLMが ls/glob でページ種別を絞れず、数百ページで探索コスト増 |
| PARA法 | 行動管理向け。知識の統合・相互参照には形式軸が適合 |
| Zettelkasten(ID付きフラット) | 人間の思考支援に最適化。ID採番はLLMにも閲覧にも不要な複雑さ |
| ライフエリア別フォルダ | 主題は重複するため置き場所が一意に決まらない |

## 但し書き(これは仮説)

この5分類は設計時の仮説であり、確定ではない。運用で「answers/ が増えない」「topics/ と concepts/ の境界で迷う」等が観測されたら統廃合する(スキーマ共進化の原則)。ページ数が少ないうちの再編コストはほぼゼロ、育ってからは高くつく。
