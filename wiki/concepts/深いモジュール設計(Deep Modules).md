# 深いモジュール設計(Deep Modules)

小さなインターフェースの背後に多くの振る舞いを隠すモジュール設計論。John Ousterhout『A Philosophy of Software Design』の deep module 概念を、AI エージェントと共有できる厳密な語彙集(glossary)として実装したのが [[Matt Pocock]] の codebase-design スキル([[Skills For Real Engineers (mattpocock skills)]])。狙いは3つ —— 呼び出し側には leverage、保守側には locality、全員に testability。

## 語彙は6語、言い換え禁止がルール

「component / service / API / boundary と言い換えるな。一貫した言語こそが要点」と明記される。これは DDD の ubiquitous language(共通言語)をコード設計語彙に適用したもの。

| 用語 | 定義 | 避ける言い換え |
|---|---|---|
| Module | インターフェースと実装を持つもの。関数〜階層横断スライスまでスケール非依存 | unit, component, service |
| Interface | 呼び出し側が正しく使うために知るべき**すべて** —— 型シグネチャに加え、不変条件・呼び出し順序・エラーモード・性能特性まで | API, signature(型表面しか指さず狭すぎる) |
| Seam | その場を編集せずに挙動を差し替えられる場所(Michael Feathers)。インターフェースが住む「位置」 | boundary(DDD の bounded context と衝突) |
| Adapter | seam でインターフェースを満たす具体物。役割の名前であり中身の名前ではない | — |
| Leverage | 深さが呼び出し側に払う配当: 学ぶインターフェース単位あたりの能力。1実装が N 呼び出し箇所+M テストで回収される | — |
| Locality | 深さが保守側に払う配当: 変更・バグ・知識・検証が1箇所に集中する。「一度直せば全部直る」 | — |

## 判定原則4つ: 深さはインターフェースの性質である

1. **深さは実装でなくインターフェースの性質** — 深いモジュールの内部が小さな交換可能部品で構成されていてよい。それらがインターフェースに漏れていないことが深さ
2. **削除テスト(deletion test)** — モジュールを消したと想像する。複雑さが消えるなら単なる素通し(pass-through)、複雑さが N 箇所の呼び出し側に再出現するなら価値を稼いでいた
3. **インターフェースがテスト面** — テストがインターフェースを突き抜けたくなるなら、モジュールの形が間違っている
4. **adapter 1つは仮説の seam、2つで本物** — 実際に何かが変わる場所にしか seam を導入しない

⚠️ 原典からの意図的な逸脱: Ousterhout の「深さ = 実装行数/インターフェース行数」比率は「実装の水増しを報酬にする」として棄却し、深さを leverage(呼び出し側の得る能力)で測り直している。原典を読む際はこの差に注意。

## 転用: この Wiki の既存設計判断に理論的裏付けを与える

- **[[ベンダーロックインしない自作Wiki基盤の設計]] の「LLM を薄い継ぎ目に隔離」はまさに seam 概念**。この語彙で言い直すと「LLM は adapter であり、Wiki のスキーマ(CLAUDE.md)が interface。モデルを乗り換えても interface が変わらないから locality が守られる」—— 既存の設計判断に理論的裏付けが付いた
- **削除テストは Wiki ページの健全性チェックに流用できる**。「このページを消したら知識はどこに再出現するか」—— 複数ページに散るなら concept ページとして価値を稼いでいる。どこにも現れないなら孤立ページ(/lint の検査対象)
- **「1つは仮説、2つで本物」は概念ページ新設の判断基準になる**。1ソースにしか出ない概念は sources ページ内の記述で足り、2ソース目が現れたら concept ページに昇格 —— という運用ルールが導ける
