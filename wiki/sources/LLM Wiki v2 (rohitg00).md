# LLM Wiki v2 (rohitg00)

Karpathyの[[LLM Wikiパターン]]の拡張版。AIエージェント用メモリエンジン[[agentmemory]]の運用経験(数千セッションと主張)から、「スケール時に何が壊れ、何が足りないか」を論じたアイデア文書。

## 主張の要点

### 1. 記憶のライフサイクル(最重要の追加提案)

原典は全知識を「永遠に等価」に扱うが、実際の知識には寿命がある:

- **確信度スコア** — 各事実に「支持ソース数・最終確認日・矛盾の有無」に基づくスコアを持たせる。時間で減衰し、再確認で強化される
- **上書き(Supersession)** — 新情報が旧記述を否定したら、注記でなく明示的に置き換える。旧版はstaleマーク付きで保存(知識のバージョン管理)
- **忘却** — Ebbinghausの忘却曲線を適用。アクセス・再確認されない事実は徐々に格下げ(削除はしない)。アーキテクチャ決定はゆっくり、一時的なバグ情報は速く減衰
- **記憶の4階層** — 作業記憶(生の観察)→エピソード記憶(セッション要約)→意味記憶(セッション横断の事実)→手続き記憶(反復から抽出したワークフロー)。証拠の蓄積に応じて上の階層へ昇格

### 2. 型付き知識グラフ

`[[リンク]]`は「AがBに関係する」しか表せない。「uses / depends on / caused / supersedes」など**関係に型を付け**、質問時はキーワード検索でなくグラフ探索(依存エッジを辿って影響範囲を発見)で答える。ページは読むため、グラフは発見のため。

### 3. 検索のスケール限界

**index.md方式は100〜200ページが限界**(インデックス自体が1回で読めない長さになる)。以降はBM25+ベクトル+グラフ探索のハイブリッド検索をRRFで融合。index.mdは人間用カタログとして残す。

### 4. イベント駆動の自動化

手動運用が原典最大のギャップ。「ソース追加時に自動ingest」「セッション終了時に洞察を自動ファイリング」「書き込み時に矛盾チェック」「定期Lint」などのフックで、簿記作業を完全自動化する。人間はキュレーションと方向付けに専念。

### 5. 品質と自己修復

- 生成コンテンツ全てに品質スコア(構造・出典・整合性)。閾値未満はフラグか書き直し
- Lintは指摘で終わらせず**自動修復**(孤立ページのリンク、壊れた参照の修理)
- 矛盾は「フラグ」から「解決提案」へ — ソースの新しさ・権威性・支持観察数で優劣を判定

### 6. 結晶化(Crystallization)

調査・デバッグなど**完了した作業スレッド全体**を構造化ダイジェスト(問い・発見・関与エンティティ・教訓)に蒸留してWikiの一級ページにする。探索の成果もソースと同格に扱う。

### 7. その他

- **プライバシー**: 取り込み時にAPIキー・認証情報・PIIを自動除去。全操作の監査ログ
- **マルチエージェント**: 複数エージェントの観察をマージ(last-write-wins+タイムスタンプ解決)、私有/共有のスコープ分け
- **導入スペクトラム**: Minimal(原典相当)→ライフサイクル→グラフ→自動化→スケール→協調、と段階導入せよ

## このWikiへの示唆(運用改善の視点)

現構成はまさに「Minimal viable wiki」。この文書が示す**現実的な次の一手**:

1. **Supersession規約** — 今の「⚠️ 矛盾:」フラグに「どちらが優勢か+旧記述のstale化」を追加(コスト小・効果大)
2. **結晶化** — Claude Codeでの大きな調査・設計セッションの結末をanswers/に蒸留する習慣
3. **プライバシーフィルタ** — raw/に置く前にAPIキー等を除去する注意をスキーマに明記
4. 確信度スコア・記憶階層・ハイブリッド検索は**数百ページ規模になるまで不要**(YAGNI)

## 評価・注意点

- [[agentmemory]]の宣伝を兼ねた文書であり、「数千セッションで実証」等の主張は未検証
- 提案の多くは重装備で、文書自身が「Minimalから始めよ」と認めている
- ただし「index.md 100〜200ページ限界」「矛盾は解決まで」「結晶化」は経験則として説得力が高い
