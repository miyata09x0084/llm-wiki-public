# LLM Wikiパターン

LLMが永続的な個人ナレッジベース(相互リンクされたMarkdown群)を構築・保守し続けるパターン。Andrej Karpathyが2026年に提唱。**このWiki自体がこのパターンの実装**である。

## 核心

RAG(毎回検索して再合成、蓄積なし)に対し、**知識を一度コンパイルして保守し続ける**。「Obsidian=IDE、LLM=プログラマー、Wiki=コードベース」。人間がWikiを挫折する原因である簿記コスト(1情報→N箇所更新)をLLMに委譲することで、初めて「腐らないWiki」が経済的に成立する。Vannevar BushのMemex(1945)の「誰が保守するのか」問題への回答。

## 系譜 — 80年間未解決だった「保守問題」の再定義がこのパターンを生んだ

発想の源流は Memex(1945)であり、系譜は「夢の提示→集団では解決→個人では挫折→保守者を AI にする」の4段階で進んだ。

1. **Memex(1945)— 夢の提示**: Vannevar Bush が論文「As We May Think」で構想した、個人の知識を連想リンクで繋ぐ機械。ハイパーテキストと Wiki の思想的祖先。ただし「リンクと索引を誰が保守し続けるのか」が未解決だった
2. **Wiki・Wikipedia — 集団なら解けた**: Ward Cunningham の Wiki 発明(1995)を経て、Wikipedia は「大勢で分担」により保守問題を社会規模で解決。しかし個人 Wiki には分担者がいない
3. **PKM ブーム(Zettelkasten・Roam・Obsidian)— 道具は揃ったが人間が挫折**: 双方向リンク等で道具は Memex の理想に近づいたが、個人 Wiki は腐り続けた。原因は道具でなく簿記コスト(1情報→N箇所更新)が人間には高すぎること
4. **Karpathy の転回(2026)**: 「足りなかったのは良い文書でも検索でもなく、実際に働く司書だ」— ボトルネックを保守労働と特定し直し、LLM に司書役を委譲した。v2 文書はこれを "The Memex is finally buildable" と表現(raw/2026-07-14-llm-wiki-v2-rohitg00.md)

補足: Karpathy はかねて「LLM = 新しい計算機の CPU、ファイル = その記憶」という LLM OS 的世界観を発信しており、このパターンはその個人知識管理への適用と読める(出典なし・LLM の一般知識。①〜③の歴史的背景も同様)。

## 構成要素

- **3層**: raw(不変ソース・人間所有) / wiki(生成ページ・LLM所有) / スキーマ(規約・共同所有)
- **3操作**: Ingest(取込・統合) / Query(索引→ドリルダウン→回答の書き戻し) / Lint(健全性チェック)
- **2ビュー**: index.md(内容軸カタログ) / log.md(時間軸・追記専用ログ)

## v2拡張([[LLM Wiki v2 (rohitg00)]]による)

スケール時の課題への拡張メニュー。段階導入が前提:

| 段階 | 追加要素 | 必要になる時期 |
|---|---|---|
| Minimal | 原典構成(このWikiの現在地) | 初日から |
| ライフサイクル | 確信度スコア・Supersession・忘却 | 矛盾が目立ち始めたら |
| 構造 | エンティティ抽出・型付き知識グラフ | 関係性の質問が増えたら |
| 自動化 | イベント駆動フック | 手動運用が億劫になったら |
| スケール | ハイブリッド検索・記憶4階層 | **100〜200ページ超**(index.md限界) |
| 協調 | マルチエージェント同期・共有スコープ | チーム利用時 |
